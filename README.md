# GPMI - Godot Portrait Model Importer

GPMI is a single-game Godot portrait replacement launcher for Godot games. It launches one explicitly selected game executable, injects ReShade, loads the `PortraitHashReplace.addon64` add-on, and replaces portrait textures by matching hashes from an externally generated `hash_db.json`.

The project still uses the XXMI Launcher shell internally, but the user workflow is now GPMI-specific: users provide a hash database and place portrait mod images in a fixed folder layout. GPMI imports those images, generates runtime `.ptrtex` files, records mod metadata, and writes the active replacement rules.

## Core idea

GPMI separates three things:

1. **Hash database**: generated by an external tool and copied into the game profile as `GPMI/hash_db.json`.
2. **User mod images**: normal image files placed under `GPMI/Mods/` in the required layout.
3. **Runtime replacements**: generated by GPMI under `GPMI/RuntimeMods/` as `.ptrtex` files, then referenced from `hash_db.json`.

Users should normally only edit the `Mods` folder and import/select outfits through the Portrait Manager UI.

## Game profile location

GPMI uses a profile folder next to the selected game executable:

```text
<game exe folder>/GPMI/
```

Example:

```text
C:/Games/ExampleGodotGame/game.exe
C:/Games/ExampleGodotGame/GPMI/
```

The selected game path must be the exact `.exe` file, not the game folder. The launcher stores that full executable path in the legacy `game_folder` config field for compatibility with the XXMI shell.

Example config shape:

```json
{
  "game_folder": "C:\\Games\\ExampleGodotGame\\game.exe",
  "custom_game_exe_name": "game.exe"
}
```

## Required user mod folder format

This is the most important user-facing rule.

All user mods go under:

```text
<game exe folder>/GPMI/Mods/
```

The required layout is:

```text
GPMI/
└─ Mods/
   └─ <character_id lowercase>/
      └─ <outfit_name>/
         ├─ Unit/
         │  └─ <one image file, name can be anything>
         └─ Unit_H/
            └─ <one image file, name can be anything>
```

Rules:

- `<character_id lowercase>` must be lowercase and must match the character id used by the hash database. Example: `mona`, `furina`, `shorekeeper`.
- `<outfit_name>` can be any folder name. GPMI will automatically assign an internal outfit id such as `outfit_001` during import.
- `Unit` must contain exactly one image.
- `Unit_H` must contain exactly one image.
- Image file names are arbitrary. GPMI does not use the original image filename for runtime identity.
- A mod is incomplete if either `Unit` or `Unit_H` is missing.
- A character is only enabled for replacement if both `Unit` and `Unit_H` hashes exist in `hash_db.json` and the selected outfit has both generated `.ptrtex` files.

Supported source image formats are currently:

```text
.png, .jpg, .jpeg, .webp, .bmp, .tga
```

Example:

```text
C:/Games/ExampleGodotGame/GPMI/Mods/mona/default/Unit/mona_normal.png
C:/Games/ExampleGodotGame/GPMI/Mods/mona/default/Unit_H/mona_high.png
```

Another valid example:

```text
C:/Games/ExampleGodotGame/GPMI/Mods/mona/swimsuit/Unit/anything.png
C:/Games/ExampleGodotGame/GPMI/Mods/mona/swimsuit/Unit_H/also_any_name.png
```

## Files generated by GPMI

When a mod is imported, GPMI generates runtime files under:

```text
<game exe folder>/GPMI/RuntimeMods/
```

Generated `.ptrtex` file names use the character id and assigned outfit id, not the source image name. This avoids collisions when different mods use the same image filename.

Example generated output:

```text
GPMI/
└─ RuntimeMods/
   └─ mona/
      └─ outfit_001/
         ├─ mona_outfit_001_Unit.ptrtex
         └─ mona_outfit_001_Unit_H.ptrtex
```

GPMI also writes:

```text
GPMI/mod_meta.json
```

`mod_meta.json` records imported characters, assigned outfit ids, source image paths, generated `.ptrtex` paths, and the currently selected outfit for each character.

Users generally should not edit `RuntimeMods` or `mod_meta.json` manually.

## hash_db.json

`hash_db.json` is generated by an external tool and should be placed at:

```text
<game exe folder>/GPMI/hash_db.json
```

The Portrait Manager has an **Import hash_db.json** button that copies an external JSON file into that location.

The hash database must contain a top-level `rules` list. A rule should include at least:

```json
{
  "enabled": true,
  "hash": "0x1234567890abcdef",
  "note": "Unit/mona/default",
  "replacement": ""
}
```

GPMI uses each rule's `note`, `character_id`, and `slot` fields to identify which character and portrait slot the hash belongs to. Legacy-style notes such as these are supported:

```text
Unit/mona/default
Unit_H/mona/default
```

When the user selects an imported outfit and clicks **Apply to hash_db**, GPMI rewrites the active runtime fields in `hash_db.json`:

- `enabled`
- `replacement`
- `character_id`
- `outfit_id`
- `slot`
- `note`

The original external hash list remains the source of truth for hashes. GPMI only links selected local outfits to those hashes.

## Why source images are converted to .ptrtex

The runtime add-on needs raw pixel data with width, height, format, and row pitch. PNG/JPG/WebP files are compressed image formats and require decoding. GPMI decodes source images during import and writes `.ptrtex` files so the injected DLL can load replacement data directly at runtime.

User workflow remains image-based: put normal images in `Mods`, then let GPMI generate `.ptrtex` files.

## Portrait Manager workflow

Open the launcher, select the exact game `.exe`, then open **GPMI Portrait Manager**.

Recommended flow:

1. Open **Setup**.
2. Click **Open Mods** or **Create Example Mod Folders**.
3. Put user mods under `GPMI/Mods/<character>/<outfit>/Unit` and `Unit_H`.
4. Click **Import hash_db.json** and select the externally generated hash database.
5. Open **Import Mods**.
6. Click **Scan Mods**.
7. Import one mod with **Import Selected**, or import all valid mods with **Import All Ready**.
8. Open **Outfits**.
9. Select a character and click **Load Character Outfits**.
10. Select an outfit and click **Select Outfit**.
11. Click **Apply to hash_db**.
12. Open **Runtime** and confirm enabled rule counts.
13. Launch the game through GPMI.

A character can be disabled from the **Outfits** tab with **Disable Character**. After disabling, click **Apply to hash_db** again.

## Runtime layout

Expected runtime layout near the game executable:

```text
<game exe folder>/
├─ game.exe
└─ GPMI/
   ├─ hash_db.json
   ├─ mod_meta.json
   ├─ ptr_config.ini
   ├─ PortraitHashReplace.log
   ├─ Dumps/
   ├─ Mods/
   │  └─ <character>/<outfit>/Unit/<image>
   │  └─ <character>/<outfit>/Unit_H/<image>
   └─ RuntimeMods/
      └─ <character>/<outfit_id>/<character>_<outfit_id>_Unit.ptrtex
      └─ <character>/<outfit_id>/<character>_<outfit_id>_Unit_H.ptrtex
```

Launcher-bundled runtime DLLs are still stored in the repository package folder:

```text
Resources/Packages/GPMI/Core/GPMI/ReShade64.dll
Resources/Packages/GPMI/Core/GPMI/PortraitHashReplace.addon64
Resources/Packages/GPMI/Core/GPMI/Addons/PortraitHashReplace.addon64
```

## Building PortraitHashReplace.addon64

If `PortraitHashReplace.addon64` is missing, build it from the kernel source:

```powershell
cd Resources\Packages\GPMI\Tools\kernel_source
.\build.cmd
```

The build script expects the ReShade SDK header at:

```text
Resources/Packages/GPMI/Tools/third_party/reshade/include/reshade.hpp
```

It also requires MSVC and CMake.

## Running GPMI

From the repository root:

```powershell
python src\xxmi_launcher\app.py
```

Quick start with an explicit executable:

```powershell
python src\xxmi_launcher\app.py "C:\Games\ExampleGodotGame\game.exe"
```

## Preflight

Run the bundled preflight check from the repository root:

```powershell
python Resources\Packages\GPMI\Tools\gpmi_preflight.py
```

Preflight checks repository files and Python syntax. Runtime DLLs may be reported as warnings if they have not been built or copied yet.

## Troubleshooting

### `hash_db.json is missing`

Use **Setup > Import hash_db.json** in the Portrait Manager. The file must be copied to:

```text
<game exe folder>/GPMI/hash_db.json
```

### `Scan Mods` reports missing Unit or Unit_H

Check the source mod folder. Each outfit must contain both folders:

```text
GPMI/Mods/<character>/<outfit>/Unit/
GPMI/Mods/<character>/<outfit>/Unit_H/
```

Each folder must contain exactly one supported image file.

### Runtime rules stay at 0

Common causes:

- `hash_db.json` does not contain hashes for both `Unit` and `Unit_H` for the character.
- No outfit is selected for that character.
- The selected outfit was not imported successfully.
- Generated `.ptrtex` files under `RuntimeMods` are missing.
- The character folder name does not match the character id used in the hash database.

### Replacement does not show in game

Check:

```text
<game exe folder>/GPMI/PortraitHashReplace.log
```

Useful log signals include loaded rule count, missing files, bad hashes, and replacement size mismatches.
